## Findings and remaining acceptance gaps

### P2 — nearest-camera normal-cone rejection is not union-camera rejection

Tracked in [issue #16](https://github.com/Yanagisawa2002/summit-gpu-systems/issues/16), with pinned source links and a runnable numerical counterexample.

`Bfp2CompactCullClusterVisible` chooses the nearest camera before its cone test. `BindCullKernelDirect` passes both multiple prepared cameras and the enabled cone flag without disallowing that combination. A near camera behind the cone can therefore remove a cluster that a farther camera should retain in the shared visible set.

For center `(0,0,0)`, cone axis `(0,0,1)`, cutoff `0`, and cameras `(0,0,-1)` and `(0,0,2)`, the current test rejects on dot `-1`; the second camera accepts on dot `+1`. A Python predicate-level check reproduced this mismatch in both camera orders. This is a mathematical reproduction of inspected logic, not execution of the shader or a captured scene failure. The option defaults off, which limits exposure but does not make the enabled combination correct.

Minimal safe direction: disable cone rejection for multi-camera groups in both binding paths, or reject only when every relevant camera safely rejects. Cover zero-distance views conservatively. Apply the rule consistently to scalar/compact/wave variants and validate against an independent visibility oracle before GPU acceptance. Runtime behavior is intentionally unchanged in the presentation PR.

### Delivery gap — the featured rendering path is not independently runnable

The [NYCGIS README](../Integrations/NYCGIS/README.md) explicitly excludes the snapshot from root compilation and lists missing host contracts. The [historical identity note](RemediationIntegration20260908.md#historical-evidence-identity) pins a retained report, not a newly recovered original measured binary/source attestation.

The new case page states both limits beside the headline result. That resolves presentation ambiguity, not the underlying delivery gap. The next acceptance target is a minimal procedural Scalar/WaveCompact/VisibleTiles renderer with real draw consumption, independent visibility/image checks, matched camera/residency settings, and source-bound raw measurements. Do not substitute the query demo for this task.

### Evidence gap — complete-task and cross-backend results must remain separate

The [sphere reuse report](SPHERE_REUSE_RESULTS_2026-09-10.md) supports a finite old/new task improvement while native Serial remains faster. Its remaining query/submission/readback interval is not decomposed into kernel, transfer, waiting and recording time. Profile that boundary before asserting which component dominates or changing the output contract.

The [planner case](WHOLE_TASK_DECISIONS.md) still marks complete-task benefit Unmeasured. The [native RTX 5090 report](whole-task-md-20260915/LINUX_5090_NUMERICAL_RESULTS.md) still marks formal performance NO-GO and the actual SUMMIT GPU force/state consumer unfinished. Neither is promoted by the revised README.

These are reported acceptance limits, not newly discovered algorithm bugs. The evidence index now makes them visible without requiring readers to combine unrelated historical documents.

## Recommended implementation order

First fix and validate union-camera cone rejection. Next make the featured no-copy renderer independently runnable. Then isolate the remaining sphere query/submission/readback costs under an unchanged complete-output contract. Additional subsystems and wider benchmark matrices are lower priority until these bounded acceptance gaps close.
